Weekly Publish Pipeline

One scheduled run that fans in from a warehouse and half a dozen third-party connectors, renders a report, pushes it to static hosting behind a gate, and announces it in two channels — in that order, never the other way around.

Names, accounts, table names, channel IDs and domains are stripped; what's left is the shape. The interesting part isn't the fetching, it's what the run is allowed to do when a source lets it down — which differs per source, by design.

The run

The split is the whole design. Revenue figures are load-bearing — publishing a plausible-looking wrong number is worse than publishing nothing, so the gate aborts. Marketing context and external registry items are garnish — losing one is worth a line of small print, not a skipped week.

The rules that hold it together

  • hard vs softEvery source is classified before the run starts. Only hard sources can abort it.
  • verify, then pushThe gate is decrypted in-process with each allowed name before anything is uploaded — a broken gate is regenerated, never published.
  • 2xx barrierAnnouncements are downstream of every upload. A half-pushed week is silent rather than misleading.
  • append-onlyThe run writes this period's two files and refreshes one index. Prior periods are never touched.
  • credential disciplineThe token is read at the call site and appears in no message, commit or log.
  • stub over garbageWhen the guard trips, the channel gets a short "skipped, retrying" note with the numbers that tripped it — not a −100% badge.
